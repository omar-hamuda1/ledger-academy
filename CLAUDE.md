# Ledger Academy — Project Rules

`docs/PROJECT_STATE.md` is a historical architecture/decision narrative (last full update 2026-09-07); `docs/archive/` holds older snapshots and session handoffs. The rules below are the current source of truth — things that have already caused real bugs or confusion in this project. Read before making changes in these areas.

## Content & language
- **Never use the word "مدرس" anywhere in the UI.** Use "محاضر" or "مدرب" instead. This is a hard, non-negotiable rule for this platform.
- **All API error messages must be Arabic**, since `data.error` strings are shown directly to users in the UI. A 2026-09-06 audit found ~15 API route files still returning English guard-clause errors ("Forbidden", "Unauthorized", "Invalid input.") left over from early scaffolding while newer business-logic errors were correctly Arabic — all were translated. Don't reintroduce an English literal in a `NextResponse.json({ error: ... })` call.
- All user-facing UI is Arabic RTL (dark navy / gold theme, Cairo font). `lang="ar" dir="rtl"` and the Cairo font are now set **once, globally, on the root `<html>`/`<body>`** in `src/app/layout.tsx` — don't remove that. Per-page `dir="rtl" lang="ar"` wrapper divs still exist in most pages as a harmless leftover from before this was centralized; no need to strip them, but don't rely on them being the only source of RTL/font — the root layout is now the source of truth.
- **English is being added as an optional second UI language (started 2026-09-08, PHASED — most of the app is still Arabic-only).** Design: cookie-based (`locale` = `ar`|`en`, no URL segment), client-side, no dependency.
  - `src/i18n/`: `config.ts` (locales, `dirOf`), `messages/{ar,en}.json` (flat `"area.key": "string"`; `ar` is authoritative, missing `en` keys fall back to Arabic then the key), `translate.ts` (`makeT(locale)` → `t(key, {vars})` with `{name}` interpolation), `LocaleProvider.tsx` (client; `useSyncExternalStore` on the cookie so there's no hydration mismatch — server snapshot is always the default; exposes `useT()` and `useLocale()`).
  - `<LocaleProvider>` wraps everything in `layout.tsx`; a pre-hydration inline `<script>` flips `document.documentElement.dir/lang` for returning English users; `<html suppressHydrationWarning>` covers the resulting attribute diff.
  - **To translate a component:** it must be `"use client"`; `const t = useT()`; replace each literal with `t("area.key")` and add the key to **both** JSON files. `LanguageSwitcher` (globe, in `LedgerHeader` + `DashboardShell`) toggles.
  - **Done so far:** `LedgerHeader`, `LedgerFooter`, `DashboardShell` (nav), all 4 auth pages + `AuthLayout`. **Not yet:** admin pages, marketing pages, course/lesson pages, API error strings, emails — these stay Arabic under `en` for now. DB content (course/lesson/quiz text) is out of scope — it renders as the admin typed it regardless of locale.
- **`/privacy` and `/terms` are real, tailored pages** (`src/app/(marketing)/privacy`, `.../terms`), not boilerplate — added 2026-09-06 because students are minors and the platform previously had zero data/legal disclosure anywhere. Both carry a visible disclaimer that they're a general template needing real lawyer review, not certified legal advice — don't remove that disclaimer, and don't present either page as legally final without the user confirming a lawyer reviewed it.

## Design system
- **shadcn/ui was added (2026-09-06)** — `components.json` (`style: radix-nova`, `rsc: true`, `rtl: true`), `src/lib/utils.ts` (`cn()`, re-exported from the `cn` npm package), components land in `src/components/ui/`. Add new primitives with `npx shadcn@latest add <name> -y`. **Its default init injects a generic light-mode-plus-`.dark`-class color system that does NOT match this app's theme** — this app is permanently dark (no light/dark toggle anywhere), so the semantic tokens (`--background`, `--foreground`, `--primary`, `--card`, `--border`, `--ring`, `--chart-1..5`, `--sidebar-*`, etc.) were manually remapped in `globals.css`'s single `:root` block directly onto the navy/gold palette instead (`--primary: #fbbf24`, `--background: #020617`, `--border: rgba(255,255,255,0.1)`, etc.) — the generated `.dark` class block was deleted since it would never apply. **If `npx shadcn add` is ever re-run and regenerates/duplicates this block, re-apply the navy/gold mapping — don't leave shadcn's default gray/white values in place**, or new components will render in the wrong (light, gray) theme. `--font-sans` is pointed at `var(--font-cairo)` (not a separate Geist font — init tried to add one; removed, this app is Arabic/Cairo-only per the rule below).
- **`framer-motion` and `recharts` were added (2026-09-06)** for animations and data-viz respectively — both plain npm packages, no account/config needed. Motion needs Client Components (`"use client"`); keep data-fetching in the Server Component page and pass plain serializable props down to a motion-enabled Client Component, rather than converting whole pages to client-side.
- Real design tokens live in `src/app/globals.css`'s `@theme` block: `--color-navy-*`/`--color-gold-*`, `--radius-card`/`--radius-control`, `--shadow-card`/`--shadow-elevated`/`--shadow-glow-gold`, `--animate-fade-in`/`-scale-in`/`-slide-up`/`-pop`. Before, `globals.css` was the untouched Next.js starter file with zero brand tokens — that's why the app had no shadows/elevation anywhere and inconsistent border-radius. **Use these tokens (`shadow-card`, `rounded-card`, `rounded-control`, `animate-*`) on new cards/surfaces instead of ad-hoc `rounded-2xl`/`shadow-none` guessing.**
- `slate-950`/`slate-900` and `navy-950`/`navy-900` are the same colors — the whole codebase was mass-renamed to `navy-*` (2026-09-06) for one consistent vocabulary. Don't reintroduce bare `slate-950`/`slate-900`/`amber-*` in new code.
- **Accessibility audit (2026-09-06, static code review only — no browser/device testing tool was available)**: images have proper `alt` text (only one real image exists in the app so far), all icon-only buttons have `aria-label`, and no keyboard-trap `onClick`-on-`<div>` patterns exist anywhere — everything interactive is a real `<button>`/`<a>`/`<Link>`. Found and fixed one real, calculated issue: `text-slate-500` on the `navy-950` background computes to a 4.24:1 contrast ratio, just under the WCAG AA minimum (4.5:1) for normal text — bumped to `text-slate-400` (7.87:1) everywhere it was real visible content (33 occurrences across 21 files), left `placeholder:text-slate-500` alone since placeholder contrast is a weaker WCAG requirement and a different UX convention. `gold-400` on `navy-950` computes to ~12:1 (excellent). Form inputs use `focus:outline-none` and rely solely on a `focus:border-gold-400` color change as their keyboard-focus indicator — legitimate but worth knowing if focus visibility is ever reported as an issue. **Real device/viewport/screen-reader testing has still never been done** — this was a code-level audit only.
- **Perf/a11y pass (2026-09-09, Lighthouse mobile, local + prod-past-the-gate)**: public pages score Best-Practices 100, SEO 100 (un-gated), CLS 0, TTFB ~60 ms on Vercel. Perf sat at 68–82 — the drag is client-side (LCP 3–4 s, TBT ~470 ms) from the Cairo web-font + framer-motion hydration, *not* the server. Fixed this round: the marketing pages + `AuthLayout` each re-instantiated `Cairo()` with a *different* option set than `layout.tsx` (no `variable`), so `next/font` loaded the family **twice** — now there's **one** Cairo instance in `layout.tsx` (`display: "swap"`, applied to `<body>`); every other file just inherits it, no local `Cairo()` call. Home a11y went 89→100: added the missing `<main>` landmark, fixed heading order (`(marketing)/page.tsx` module `<h3>`, Hero's mockup line is now a `<p>`, `(marketing)/courses` has an `sr-only` `<h2>`), and the "3 steps" `<ol>` now has `<li>` as direct children with the decorative connector line moved out of the list. Still open: trim first-load JS (framer-motion lazy-load), which is the remaining TBT lever.
- Duplicated JSX is a real recurring problem here (the course-card markup was copy-pasted verbatim across two pages before being extracted into `src/components/ledger-academy/CourseCard.tsx`) — if you're about to paste the same card/block into a second file, extract a shared component instead.
- `sonner` (toasts, mounted globally in `src/components/providers.tsx`) and `canvas-confetti` are installed for student-facing feedback (lesson complete, quiz pass). Reuse these rather than adding a different toast/confetti library.
- **Reading `localStorage` in a client component: use `useLocalStorage` from `src/lib/use-local-storage.ts`, not `useEffect(() => setState(localStorage.getItem(...)))`.** The `eslint-plugin-react-hooks` v6 rules that ship with Next 16 (`react-hooks/set-state-in-effect`) flag the effect pattern as an error, and it also causes an SSR/first-paint flash. The hook wraps `useSyncExternalStore` (server snapshot returns `null`, so no hydration mismatch), keeps multiple instances on the same key in sync within the tab via a custom event, and falls back to an in-memory store if `localStorage` itself throws (Safari "block all cookies", some webviews) so controlled inputs still work. `AnnouncementBanner`, `LessonWorkspacePanel`, and `SwotBoard` all use it.

## Routing
- **Dashboard routes are real folders (`src/app/dashboard/admin`, `src/app/dashboard/student`), never a `(dashboard)` route group.** A route group's parentheses are stripped from the URL — using one here would silently break the dashboard auth check in `src/middleware.ts` (which keys off the `/dashboard` path prefix) and every existing link. This was deliberately fixed once already; don't reintroduce it.
- **`src/middleware.ts` does three things**: (1) a `STAGING_PASSWORD` privacy gate (opt-in via env var — inert when unset; when set, the whole site returns an Arabic password page / API 401 / `noindex` until unlocked via `/staging-unlock`), (2) a redirect of **logged-in non-admins hitting `/` → `/dashboard/student`** (students have no use for the marketing home; `getToken` reads the JWT, no DB — `ADMIN`s pass through so they can preview the public site, and `/?home` is an escape hatch that skips the redirect), and (3) the NextAuth `withAuth` guard for `/dashboard/*` (`ADMIN`-only for `/dashboard/admin`, plus the permission-scope backstop), composed in unchanged. The marketing header's logo also points at the dashboard for a logged-in student (`LedgerHeader.tsx`). The `matcher` is site-wide (`/((?!_next/static|_next/image|favicon.ico).*)`) so the gate can cover everything — the dashboard-vs-not distinction is a path check inside the middleware, not the matcher. Don't narrow the matcher back to `/dashboard/:path*` or the gate stops protecting the marketing/API routes.
- Login redirects by role: `ADMIN` → `/dashboard/admin`, everyone else → `/dashboard/student`. Don't hardcode a single redirect target.

## Security-critical invariants (found broken once, must never regress)
A full audit on 2026-09-06 found and fixed several real, exploitable bugs. These are now-enforced invariants — don't remove the checks that make them true:
- **Every route that writes `LessonProgress` or `QuizAttempt` (or renders lesson/quiz content) must verify the caller is enrolled in that content's course** (`db.enrollment.findUnique({ where: { userId_courseId: {...} } })`). Before the fix, `/api/progress`, `/api/quizzes/[id]/attempts`, and the lesson-detail page all trusted a client-supplied `lessonId`/`quizId` with no ownership check — meaning any logged-in user (even paying for nothing) could fabricate progress, harvest quiz answer keys (`correctId` was returned in the response), and read paid lesson content by guessing/observing IDs, none of which are secret (they're plain cuids visible in network requests). If you add a new student-facing route that reads/writes per-lesson or per-quiz data, it needs this same check.
- **Enrollment (`Enrollment` row creation) happens in exactly these places, nowhere else.** Do not add a "just create an Enrollment row" endpoint — a `POST /api/enrollments` used to exist that skipped every check, letting any user enroll in any paid course for free. It was deleted, not fixed.
  - `/api/checkout`: **free courses only** now (`price <= 0` → `enrollment.upsert`; paid → 403). Stripe was removed entirely (2026-09-07) — it never supported Egypt-based merchants. No online card payment anywhere in the app.
  - The **student dashboard** (`/dashboard/student`) has a "كورسات متاحة" section (2026-09-09) listing every published course the student isn't enrolled in — free ones enrol inline via `/api/checkout`, paid ones link to `/courses/[slug]` for the code-order flow, and a course with a `PENDING` code order shows "طلبك قيد المراجعة". This is so a logged-in student never needs the marketing site to get more courses (paired with the middleware `/` → dashboard redirect). It surfaces the existing enrolment paths — it does **not** add a new one.
  - `/api/prepaid-codes/redeem`: a student submits a `PrepaidCode` (single-use, course-scoped, generated in batches by the admin at `/dashboard/admin/prepaid-codes`). Guarantees that must not regress: **(1)** the single-use claim is an atomic `updateMany({ where: { id, isUsed: false } })` inside a `$transaction` with the `enrollment.create` — a racing second redeem updates 0 rows and gets 409; **(2)** if `enrollment.create` throws `P2002` the whole transaction rolls back, so the code is **not** burned; **(3)** an explicit pre-check rejects redemption (without consuming the code) when the student is already enrolled; **(4)** an optional `courseId` in the body is verified against the code's own `courseId`; **(5)** rate-limited per user and per IP. Regression tests: `tests/api/prepaid-code-redeem.test.ts`.
  - `/api/code-orders` review (admin approve): approving a pending `CodeOrder` issues a `PrepaidCode` (already `isUsed`, `usedById` = the requester) **and** creates the `Enrollment`, in one `$transaction`. This is how a student "buys" access for a paid course — they submit a request with a **required payment-proof screenshot** (uploaded via `POST /api/uploads/payment-proof` → Neon Object Storage, key checked to be under the caller's own `proofs/<userId>/` prefix) plus a manual-transfer reference; the lecturer views the screenshot (short-lived presigned URL) and approves. Approve/reject both `notify()` the student; a new request `notify()`s all admins. (Added 2026-09-07 alongside the Stripe removal.)
- **Deleting a `Lesson` or `Module` must clean up `LessonProgress` and `Quiz`/`QuizAttempt` first**, inside a transaction, before the delete — both FKs are `ON DELETE RESTRICT` in the schema, so a naive `db.lesson.delete()`/`db.module.delete()` throws an uncaught 500 the moment any student has interacted with that lesson. `src/app/api/lessons/[id]/route.ts` and `src/app/api/modules/[id]/route.ts` show the correct pattern (mirrors the pre-existing, correct `QuizAttempt` cleanup in `src/app/api/quizzes/[id]/route.ts`).
- **`/api/auth/otp/send` deletes any previous unverified code for that email+purpose before creating a new one.** Without this, requesting a resend and then entering the *first* email's code fails against the newer DB row and burns an attempt on a code the user never typed — `otp/verify` only ever checks the single latest row by design, so there must only ever be one live row.
- **The platform must always keep at least one active ADMIN.** `PATCH /api/users/[id]` (admin promote/demote + disable/enable + password reset, added 2026-09-07) refuses to demote or disable the last `role: ADMIN` with `disabledAt: null` (`409`), and refuses to let an admin edit their own row at all (`400`). Don't remove those checks. A disabled account is blocked at **login** (`authorize()` in `src/lib/auth.ts` throws when `user.disabledAt` is set) — an **already-issued JWT session stays valid until it expires**, so disable is not an instant kill-switch; that's a known, accepted limitation (a per-request DB check was deliberately not added). The `setPassword` action (admin-supplied ≥8 chars, or a server-generated `randomBytes(9).base64url`) bcrypt-hashes and returns the plaintext **once** in the response for the admin to relay — it is never logged (`user.password_reset` audit records only `{ generated }`). Regression tests: `tests/api/users-manage.test.ts`.
- **`DELETE /api/users/[id]` hard-deletes an account** (added 2026-09-09) — irreversible, "disable" stays the non-destructive path. `src/lib/delete-user.ts` (`deleteUserCascade`) removes everything RESTRICT-linked in one transaction (enrollments, progress, quiz attempts, certificates, their reviews, their Q&A, notifications targeted at them, notification reads, prepaid codes they redeemed, code orders they requested, their audit-log rows, their OTP rows) and **nulls** attribution on artifacts that outlive them (`Notification.createdById` for broadcasts they composed, `CodeOrder.reviewedById` for orders they approved). Guards: not self (400), not a protected super-admin unless caller is one (403), and **not an instructor who still owns courses** (409 — `Course.instructorId` is RESTRICT and the cascade deliberately doesn't touch courses; reassign/delete them first). UI: a "حذف نهائي" button in `UserRowActions.tsx` that requires typing the target's email. Tests: `tests/api/user-delete.test.ts`.
- **`DELETE /api/courses/[id]` hard-deletes a course** (added 2026-09-09) — irreversible; unpublishing (`isPublished: false`) is the non-destructive path. `src/lib/delete-course.ts` (`deleteCourseCascade`) runs one `$transaction`: clears the RESTRICT relations deepest-first (`QuizAttempt`, `Quiz`→cascades `Question`, `LessonProgress`, `Enrollment`), deletes `CodeOrder` **before** `PrepaidCode` (the `CodeOrder.prepaidCodeId` FK is RESTRICT), deletes `Certificate` + `Review`, then `course.delete()` — which DB-cascades `Module`→`Lesson`→(`Resource`, `LessonQuestion`→`LessonAnswer`). Not cleaned: payment-proof blobs for the deleted code orders (orphaned in the bucket, same as `deleteUserCascade`) and notification `href`s that pointed at the course. `requireScope("courses")`; audit `course.delete` with `{ slug, title, enrollments, certificates }`. UI: a trash icon in the `/dashboard/admin/courses` row (`DeleteCourseButton.tsx`) that requires typing the course **slug**. This is also how you clear the "owns courses" 409 blocking a `DELETE /api/users/[id]` on an instructor. Tests: `tests/api/course-delete.test.ts`.
- **`User.superAdmin` accounts are protected** (added 2026-09-08). `PATCH /api/users/[id]` returns `403` ("لا يمكن تعديل حساب مسؤول رئيسي.") on `setRole`/`setDisabled`/`setPassword` when the target has `superAdmin: true` and the caller is **not** themselves a super-admin — a peer super-admin still can. There is **no API or UI path to grant/revoke the flag**: the only way in is `npm run admin:super -- --email <e>` (`scripts/set-super-admin.ts`, direct DB; `--revoke`, `--list`) or `admin:recover --super`. That CLI-only design is what makes the protection real — a regular admin can never reach a protected row or the flag. Don't add an action/endpoint that writes `superAdmin`. The admin users table shows a "مسؤول رئيسي" badge and hides the row actions (a "حساب محمي" note) for non-super viewers. Super-admins are still plain `role: ADMIN` for every other check (`requireAdmin`, middleware, redirects, notify-all-admins) — no enum value was added.
- **Admin permission scopes** (added 2026-09-09). `User.restrictedScopes String[] @default([])` is a **deny-list**: empty = full access (every existing/new admin), a super-admin removes a section by adding its key. Keys + labels + `adminHasScope()` + `scopeForPath()` live in `src/lib/authz.ts`: `courses` (courses/modules/lessons/quizzes/resources/lesson-Q&A moderation), `progress`, `users`, `codes` (prepaid codes + code orders), `notifications` (broadcasts), `settings`, `reviews`, `audit`. **Super-admins are never subject to scopes and cannot be given one.** Enforcement is three layers: (1) **API** — `requireScope(scope)` replaces `requireAdmin()` in every mutating admin route (`src/lib/require-admin.ts`; returns null → the route's existing Arabic 403). `requireAdmin()` now also returns the fresh `superAdmin` + `restrictedScopes` (one PK read, already there). Kept on plain `requireAdmin()`: `GET /api/notifications` (bell poll, every admin needs it) and the Q&A **ask/answer** routes (`requireAdmin` there is role-detection for `byInstructor`, not a gate — enrolled students post too). (2) **Pages** — `requireScopePage(scope)` at the top of every scoped admin `page.tsx` (redirects a restricted admin to `/dashboard/admin?denied=<scope>`, which the home surfaces as a notice); the admin `layout.tsx` does one fresh read and passes `superAdmin`/`restrictedScopes` to `DashboardShell`, which filters the sidebar. (3) **Middleware** — a JWT-based redirect backstop in `src/middleware.ts` (`scopeForPath`); the token carries `superAdmin` + `restrictedScopes`, set at login only, so this layer can lag a change by up to the 24h token refresh — layers 1 & 2 are fresh-from-DB and authoritative, same trade-off as role changes. **The only writer of `restrictedScopes` is the `setPermissions` action on `PATCH /api/users/[id]`** — super-admin-only (403 otherwise), target must be a non-super `role: ADMIN` (400), audit `user.permissions_change`. Never add another writer. UI: `AdminPermissionsModal.tsx` opened from a super-admin-only "الصلاحيات" button in `UserRowActions.tsx`; the users list shows a "صلاحيات محدودة" badge. Tests: `tests/api/admin-permissions.test.ts`.

## Testing
- `npm test` (Vitest) runs regression tests for the 5 security-critical invariants above — this project had **zero automated tests** until 2026-09-06; before this, every fix was only verified once by hand and had no protection against silently regressing later.
- Tests run against a **dedicated Neon branch named `test`** (copy-on-write off production, created via `neon branches create --name test`), never the real dev/production database. Its connection string lives in `.env.test` (gitignored). `tests/setup.ts` loads it with `override: true` and hard-fails if `DATABASE_URL` doesn't contain that branch's host — this is a deliberate safety guard, don't remove it.
- `next-auth`'s `getServerSession` is mocked per test file (`vi.mock("next-auth", ...)`) to control the caller's identity/role; routes are imported and invoked directly (`POST(request)`, `DELETE(req, { params })`) rather than through a running server.
- **Always create/tear down fixtures via `tests/helpers/fixtures.ts`** (`createUser`, `createCourse`, `createLessonWithQuiz`, `enroll`, `cleanupCourse`, `cleanupUser`), never raw `db.course.delete()`/`db.user.delete()` in a test file directly. `Enrollment`, `LessonProgress`, and `Quiz`/`QuizAttempt` all have `RESTRICT` foreign keys back to `Course`/`User`/`Lesson` — deleting a course or user that still has an enrollment (or similar) silently fails if the call is wrapped in `.catch(() => {})`, which is exactly the leak this project's own tests hit once already (two test files bypassed the shared helper and it took a manual DB check to notice the test branch was accumulating leftover fixtures across runs). `cleanupCourse` handles the correct deletion order; use it.
- Coverage today is deliberately a starting slice, not exhaustive (15 files / 50 tests as of 2026-09-07): the enrollment-IDOR fix (`/api/progress`), the quiz answer-key/paywall fix (`/api/quizzes/[id]/attempts`), both delete-cascade fixes (`/api/lessons/[id]`, `/api/modules/[id]`), the OTP-resend-invalidation fix, a static guard that `/api/enrollments` was never recreated, prepaid-code redemption + delete, code orders + cancel, notifications, module/lesson reorder, user management (role / disable / password reset / disabled-admin guard), and quiz delete. The lesson-order-collision fix doesn't have a test yet.
- `tests/setup.ts` also `vi.mock`s `next/server`'s `after()` to run its callback inline — routes call `after()` for post-response work (alerts, blob cleanup) and the real one throws outside a request scope. It likewise no-ops `next/cache`'s `revalidatePath`/`revalidateTag` (they need a request-scoped static-generation store) so routes that bust ISR caches — course create/update/delete via `revalidateCourseSurfaces()` — are callable in tests.
- **`npm run shots [baseURL] [outDir]`** (`scripts/shots.mjs`, Playwright) screenshots `/`, `/courses`, `/courses/<slug>` at desktop + mobile. Start the app first (`npm run build && npm start`, no staging gate on localhost). Extend it for other pages when doing UI work — several real bugs (a mobile page-overflow, the hero layout) were only caught by looking.

## Pricing & payments
- **There is no online payment integration.** Stripe was removed on 2026-09-07 (it never supported Egypt-based merchants, and Paymob/Fawry need a business registration the owner doesn't have yet). A course's `price` is a **display figure only** — it tells the student how much to transfer manually (Vodafone Cash / InstaPay / bank / cash). Access is then granted by a prepaid code or an approved `CodeOrder` (see the enrollment invariant above). Do not re-add a card-payment SDK/route without an explicit decision.
- Course prices are **Egyptian Pounds (ج.م)**, not USD. Use `formatEgp()` from `src/lib/format.ts` for display — never re-introduce `$`/`"usd"`.
- **Minimum paid price is `MIN_EGP_PRICE` (20 ج.م) from `src/lib/pricing.ts`, or exactly 0 for free.** Enforced in the admin course-create/price-save routes; keep it — it's just a sanity floor now (the original reason, Stripe's per-currency minimum, is gone).
- Quiz/exam scoring must always be computed server-side. Never send `correctId` (or any answer key) to the client before grading.

## Quizzes
- A quiz is **per-lesson** (`Quiz.lessonId @unique`) — there is no standalone "exam" entity. MCQ only (`Question`: `text`, `options` Json `[{id,text}]`, `correctId`), 2–6 options. Created/edited only through the lesson editor (`/dashboard/admin/lessons/[lessonId]`).
- **`Quiz.timeLimitSec Int?`** (2026-09-08, `PATCH /api/quizzes/[id]` via `updateQuizSchema`, 60 s – 3 h or null). Null = untimed. When set, `QuizTakerForm` counts down from page-open and **auto-submits at zero** (`submitAnswers(true)` — whatever's selected, blanks scored wrong). Admin sets it in minutes via `QuizSettingsForm` on the lesson editor; the student quiz list shows a "⏱ N دقيقة" chip.
- **The timer is enforced server-side** (2026-09-09, `src/lib/quiz-timer.ts`). The quiz page mints an HMAC start token (`signQuizStart(quizId, userId)` — payload `quizId.userId.timestamp`, signed with `NEXTAUTH_SECRET`, stateless/no DB); `QuizTakerForm` sends it back in the `POST /api/quizzes/[id]/attempts` body. For a timed quiz the route rejects (400) a submission with a missing/tampered/wrong-user token or one older than `timeLimitSec + 30 s` grace. `POST /api/quizzes/[id]/start` (session + enrolled) issues a fresh token, which the client fetches on **retry** so the countdown restarts from a server-known instant. Still not full anti-cheat — a page refresh mints a new token and attempts are unlimited — but it closes "leave the tab open / edit the client countdown / submit with JS off". Tests: the "timed quiz" block in `tests/api/quiz-attempts.test.ts`.
- **Bulk import** (2026-09-08): `POST /api/quizzes/bulk { lessonId, csv, mode }` (admin) — parses a CSV via `src/lib/exam-import.ts` (`parseExamCsv`), creates the lesson's quiz if absent, then `question.createMany` in a `$transaction`. **All-or-nothing**: any bad row → 400 with a `rowErrors: string[]` list, nothing written. `mode` `"append"` (default) or `"replace"` (deletes existing questions first). Cap `MAX_QUESTIONS_PER_IMPORT` (200); envelope guarded by `bulkQuestionsSchema`. CSV columns: `question`, `option1`..`option6`, `correct` (accepts `1`-`6`, `A`-`F`, Arabic `أ`-`و`, or exact option text). `option`-id scheme is `opt-<n>`, same as `AddQuestionForm`. UI: `BulkQuestionsUpload.tsx` on the lesson editor (client reads the file as text, `examCsvTemplate()` powers the "تنزيل نموذج" download — needs UTF-8). No XLSX support (CSV only, deliberately dependency-free).

## Certificates
- A `Certificate` (one per `(userId, courseId)`) is issued when a student has **completed every lesson** in an enrolled course (`isCourseComplete()` in `src/lib/certificates.ts` — a course with 0 lessons can't complete). `POST /api/certificates { courseId }` is student-triggered and **idempotent** (returns the existing serial). It does not gate on quiz scores.
- `serial` is the public id — `/certificates/<serial>` (top-level route, not in `(marketing)`, so the print layout is clean) renders the certificate and doubles as the verification page (unknown serial → "غير صالحة"). Serials use a no-ambiguous-chars alphabet (`generateSerial()`).
- The certificate shows `course.instructor.name` — note the course-detail page currently hardcodes "محمد حسين" instead of reading the relation; the cert uses the real relation, so keep the instructor user's `name` correct.

## Reviews
- A `Review` (one per `(userId, courseId)`, rating 1–5 + optional `body`) is written by **enrolled** students only. `POST /api/reviews` upserts — no separate edit endpoint. `hidden` is admin moderation: hidden reviews are excluded from `courseRating` (avg + count) and `courseReviews` (both in `src/lib/reviews.ts`). ## Lesson Q&A

## Forms & user input
- **Signup name validation** lives in `src/lib/validators/name.ts` (`displayNameError` + `normalizeName`) — a single pure module used by **both** `registerSchema` (`superRefine` + `transform`) and the register form's client-side pre-check, so the two never drift. Rules: 2–80 chars after whitespace-collapse, ≥2 letters (`\p{L}`), no digits, no URL-ish substrings. The stored `User.name` is the normalized value. The register route surfaces the specific Arabic message for a `name` (or `guardianConsent`) issue instead of the generic "بيانات غير صالحة.".
- **Never auto-derive a URL slug from an Arabic title.** A naive `slugify()` that strips non-`[a-z0-9]` characters removes 100% of Arabic text, so it silently produces a garbage slug like `-` (which the old regex `^[a-z0-9-]+$` accepted as "valid," creating a real course with a broken URL). The course-creation form (`CreateCourseForm.tsx`) requires the admin to type the slug in English directly — don't try to reintroduce auto-fill-from-title. The slug regex (`createCourseSchema`) requires at least one real alphanumeric segment, not just hyphens; keep it that way.

## Authentication (email OTP)
- Signup and password reset both require a verified 6-digit OTP sent to the user's **email** (not phone/SMS — SMS was tried first but every provider, including Twilio and Firebase Phone Auth, charges per message with no real free tier, and Egypt is excluded from most trial programs). Signup is a two-step client flow: collect name/email/password → send OTP → verify + create account in one submit.
- **Guardian consent is required at signup** (added 2026-09-09 — students are minors). The step-1 form has a required checkbox ("I'm the guardian and consent / the student is 18+") plus optional guardian name + phone. `registerSchema` (`src/lib/validators/otp.ts`) enforces `guardianConsent: z.literal(true)` — a missing/false value is a 400 with an Arabic guardian-specific message. `POST /api/register` stamps `User.guardianConsentAt = now()` and stores `guardianName`/`guardianContact` (nullable). Accounts created before this, and any `admin:recover`/`admin:super`/seed accounts, have `guardianConsentAt = null`; the admin users list shows "✓ إقرار ولي الأمر (+ details)" or an amber "لا يوجد إقرار ولي أمر" per STUDENT row. Tests: `tests/api/register.test.ts`.
- OTP codes are 6 digits, **hashed with bcrypt before storage** (`OtpCode.codeHash`) — never store or log the plaintext code outside of `sendOtpEmail`'s dev-mode fallback.
- `src/lib/email.ts` sends via **Gmail SMTP** (`nodemailer`, `service: "gmail"`) when `GMAIL_USER`/`GMAIL_APP_PASSWORD` are set; otherwise it logs `[EMAIL DEV MODE] to <email>: ...` to the server console so the flow is testable without an email account (same nullable-client pattern `src/lib/rate-limit.ts` uses for Upstash). `sendMail` rejects on SMTP failure (so `/api/auth/otp/send` surfaces a 500 rather than silently claiming success). `EMAIL_FROM` defaults to `GMAIL_USER` (Gmail rewrites the `From` unless it's a verified alias); `EMAIL_FROM_NAME` (optional, defaults `Ledger Academy`) sets the display name. Provider history: Resend (2026-09-06, dropped — free sender only reaches the account owner) → SendGrid (2026-09-06, never activated) → Brevo (2026-09-07, **suspended by Brevo for "suspicious activity"** the moment a live test send hit the fresh free account with a `@gmail.com` sender) → **Gmail SMTP (2026-09-08)**. Gmail SMTP is a **stopgap**: ~500 msgs/day cap, and a freemail sender lands in spam for many recipients. The real fix is a custom domain with SPF/DKIM through a transactional provider — do that before scaling. `nodemailer` is pinned to `^10` via `overrides` (next-auth's optional peer wants `^7` but we don't use its email provider; 10.x has fixes the 7.x line never got).
- A verified `OtpCode` row is **deleted** the moment it's consumed by `/api/register` or `/api/auth/reset-password` — this is the replay-protection mechanism. Don't switch to a boolean "used" flag without also enforcing single-use some other way.
- Both `/api/register` and `/api/auth/reset-password` require the matching `OtpCode.verifiedAt` to be within a 15-minute window — this is intentionally generous (not a short-lived token) so the client doesn't need a separate expiry countdown.
- `/api/auth/reset-password` **rejects a new password equal to the current one** (`bcrypt.compare` before hashing, 400) — the OTP is *not* consumed on that rejection, so the user can retry within the window. This is current-password-only; there's no password-history table (reusing an older-but-not-current password is allowed). Test: `tests/api/reset-password.test.ts`.
- OTP send/verify are rate-limited both by email and by IP (`checkRateLimit`) — keep both when touching these routes.
- **Login is rate-limited** by lowercased email (`login:<email>`, 5 / 5 min) in `authorize()`. On limit it *throws* an Arabic message (as does the disabled-account case). NextAuth surfaces a thrown `authorize()` error to the client as `result.error === "<that message>"`, vs `"CredentialsSignin"` for a plain wrong-password (null return) — so `login/page.tsx` shows the generic "wrong email or password" **only** for `"CredentialsSignin"` and passes any other `result.error` straight through. Don't revert that to a blanket generic message or the rate-limit / disabled notices vanish again.
- There is no phone number field anywhere in this app — it was added, then removed, during the OTP channel pivot. Don't reintroduce one without a real reason.
- **JWT sessions, `maxAge` 7 days** (`authOptions.session`, cut from NextAuth's 30-day default 2026-09-07). The token refreshes on activity (`updateAge` 24 h), so active users aren't logged out — this only bounds abandoned/stolen sessions. `requireAdmin()` does one indexed PK re-read of the account and rejects a disabled or no-longer-ADMIN caller, so demote/disable takes effect on the *next* admin request rather than at token expiry. Student `disabledAt` is only enforced at login (`authorize()`); an existing student session persists up to 7 days — accepted (no per-request DB check on the student path).
- **Admin password reset** (`setPassword` action on `PATCH /api/users/[id]`, 2026-09-07): admin supplies a password (≥8) or leaves it blank for a generated `randomBytes(9).base64url` one; the plaintext is returned once in the response for the admin to relay and is **never logged** (`user.password_reset` audit records only `{ generated }`). Kept as an admin-side path even though self-service email reset (Brevo) works — useful when a user can't access their inbox.
- **Admin lockout recovery**: `npm run admin:recover -- --email you@example.com --password "NewPass123"` (`scripts/admin-recovery.ts`) sets a user's password directly in the database and forces `role: ADMIN`, bypassing the email-OTP flow entirely — created 2026-09-06 because this project has only ever had a single ADMIN account, and normal password reset for that account depends on the same email system that isn't always working (a real, previously-unrecoverable lockout risk). Requires direct filesystem/`DATABASE_URL` access already, so it adds no new attack surface. Upserts by email, so it also works to bootstrap a fresh admin from scratch if the database ever loses its only one.

## Lesson video progress
- `VideoPlayer.tsx` is a **client** component that auto-tracks watching: it pings `POST /api/progress` with `watchedSec` (throttled ~12s, and on pause/end/pagehide) and, at **≥90% watched**, sends `completed: true` — no button. It also **resumes** playback at the saved `watchedSec`. `MarkCompleteButton` stays as a manual fallback.
- Works for **direct files** (`<video>` events) and **YouTube** (the IFrame API — `www.youtube.com` is in the CSP `script-src`). Other embeds render in a plain `<iframe>` with no tracking. `videoKind()` / `youTubeId()` in `src/lib/video-url.ts`.
- `POST /api/progress` is **monotonic**: `watchedSec` only ever increases (scrubbing back can't lose it) and `completed` can't be flipped back to false through this route. Rate-limited (150 / 5 min / user — the player pings often).

Don't build a file-upload-to-storage feature for lesson videos without re-raising this tradeoff with the user first.

## Notifications
- **One `Notification` model does both targeted and broadcast:**
  - `targetUserId` **set** → delivered to that one user. System events use this: `CodeOrder` approve/reject → the student; a new `CodeOrder` request → all admins (one row each). Written via `src/lib/notify.ts` `notify({ userId | userId[], title, body, href? })` — **best-effort** (try/catch, never throws, like `logAudit`).
  - `targetUserId` **null** → broadcast to `STUDENT`s. One row regardless of student count. The admin composes these at `/dashboard/admin/notifications` (`POST /api/notifications`, audit-logged `notification.broadcast`); written via `broadcastToStudents(...)` (not best-effort — the compose route awaits and surfaces failure).
- **`Notification.audience`** (enum `NotificationAudience`, added 2026-09-08) applies only to broadcasts: `CURRENT_STUDENTS` (**default**) is seen only by students whose `createdAt <= notification.createdAt` — i.e. those already registered when it was sent; `ALL_STUDENTS` is seen by everyone including later signups. This fixes new signups inheriting the entire broadcast backlog. The compose form has a required radio; existing rows migrated to `CURRENT_STUDENTS`, which is why the old broadcasts stopped showing to brand-new accounts. `audience` is meaningless for targeted rows (visibility there is just `targetUserId == you`) — `notify()` doesn't set it.
- **Read state is `NotificationRead` (a row per `(notificationId, userId)`), not a column on `Notification`** — so a broadcast doesn't need a read flag per student. Unread = visible notifications with no matching `NotificationRead`. `visibleNotificationsWhere(userId, role, userCreatedAt)` in `src/lib/notifications.ts` is the shared "what this user can see" filter (their targeted ones + broadcasts if a student, bounded by `audience`/join date); use it in any route that reads/marks notifications — both callers pass the caller's `createdAt` (one extra PK read).
- `NotificationBell` in `DashboardShell`'s header (shadcn `Popover`) polls `GET /api/notifications` every 60s + on window focus; `POST /api/notifications/read` (`{ id }` or `{ all: true }`) creates `NotificationRead` rows only for notifications the caller can actually see. No email — SendGrid isn't active; if wired later, add an email alongside `notify()`, don't replace it. Not real-time push (SSE/WebSocket) on purpose — serverless target, no deployment yet.

## Database
- Database is **Postgres on Neon** (`prisma/schema.prisma` datasource is `postgresql`). Connection vars (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `NEON_BRANCH`) live in `.env` (pulled by the Neon CLI); app secrets (`NEXTAUTH_*`, `BREVO_API_KEY`, `EMAIL_FROM*`, `UPSTASH_*`) live in `.env.local`. Next.js loads `.env` then `.env.local` with `.env.local` taking precedence — **don't put `DATABASE_URL` in `.env.local`**, it would silently shadow the real one.
- The datasource has **both `url` (pooled, `-pooler` host) and `directUrl = env("DATABASE_URL_UNPOOLED")` (non-pooler)** — added 2026-09-08 after a prod `migrate deploy` failed with `P1002` "timed out trying to acquire a postgres advisory lock" over the transaction pooler. Prisma Migrate now connects directly; the app runtime still uses the pooled `url`. **Every environment that resolves the schema needs `DATABASE_URL_UNPOOLED` set** — `.env`, `.env.test` (its own test-branch non-pooler host), Vercel Production, and CI (both jobs mirror `DATABASE_URL` into it since CI never migrates; without it `prisma validate` errors "env var not found"). The direct URL is just the pooled one with `-pooler` removed from the host.
- Even on the direct connection the advisory lock kept timing out (Neon compute cold-start), so `vercel.json`'s `buildCommand` runs `migrate deploy` with **`PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK=1`** — the lock only guards against two concurrent `migrate deploy` runs, which Vercel prod builds don't do. Keep that prefix.
- **Schema changes go through Prisma Migrate** (adopted 2026-09-08, baseline `0_init`; `prisma/migrations/` is committed). Workflow for a new change:
  1. Edit `prisma/schema.prisma`.
  2. `set -a && . ./.env.test && set +a && npx prisma migrate dev --name <short_desc>` — **always source `.env.test` first**; without it, `prisma.config.ts`'s `import "dotenv/config"` loads `.env` and `migrate dev` would run against **production**. This writes `prisma/migrations/<ts>_<desc>/migration.sql` and applies it to the test branch.
  3. Commit the migration folder with the code.
  4. Push. Vercel's `buildCommand` (`vercel.json`) runs `prisma migrate deploy` against prod on every deploy, so the new migration applies itself — no manual prod step.
  - CI (`build-and-test`) does **not** run `migrate deploy`; it builds + tests against the already-migrated test branch. Local dev: after `migrate dev`, restart `next dev`.
  - Do **not** use `prisma db push` anymore — it would desync the DB from the migration history.
- Don't upgrade `prisma`/`@prisma/client` past the v6 line without checking first — v8 ("Prisma Developer Platform") has a completely different CLI with no `migrate dev`/`generate` commands and broke the whole workflow when it got installed once by default.
- After schema changes, **restart the dev server** — a long-running `next dev` process holds a stale `@prisma/client` in memory even after it's regenerated on disk, and will 500 on any new field/model until restarted. On Windows this can also show as `EPERM` renaming the query engine `.dll`; kill stray node processes on port 3000 and retry.
- The old local `prisma/dev.db` SQLite file and the stale SQLite-dialect `prisma/migrations/` folder were both deleted (2026-09-06) — inspected first via Node's built-in `node:sqlite`, confirmed everything in it (2 placeholder test users, a junk "koko" lesson, an empty quiz, zero enrollments) was throwaway test data with no real content, and the courses/lessons were already duplicated in Postgres from the seed. Nothing to migrate.
- **Neon free plan → only 6 h of point-in-time recovery** (`history_retention_seconds: 21600`). On top of that, `.github/workflows/backup.yml` takes a nightly `pg_dump` of prod, kept as a 90-day GitHub artifact (needs the `BACKUP_DATABASE_URL` repo secret = the non-pooler prod string). So the real recovery window is ~1 day, not 6 h — but a longer Neon retention is still a cost decision if it matters.

## Performance (pre-scale prep)
- Public marketing pages with no per-user server-rendered content (`(marketing)/page.tsx`, `(marketing)/courses/page.tsx`, `(marketing)/pricing/page.tsx`) use `export const revalidate = 300` (ISR) instead of `force-dynamic`, to cut database load on the highest-traffic pages. **`(marketing)/courses/[slug]/page.tsx` deliberately stays `force-dynamic`** — it reads `getServerSession` server-side to render a personalized enroll-button state, and caching that would risk showing one user's enrollment status to another. Don't convert it to ISR without removing that per-request session read first.
- Admin list pages (`users`, `progress`, `courses`) are paginated (`PAGE_SIZE = 20`, `skip`/`take` in Prisma, shared `src/components/admin/Pagination.tsx` component reading a `?page=` search param). Follow this exact pattern for any new admin list rather than an unbounded `findMany`. `Pagination` takes an optional `query` prop — pass the active filters so page links keep them.
- The **users** list also has search + filters (2026-09-08): `?q=` (name/email `contains`, insensitive), `?role=`, `?status=active|disabled`, read server-side into one `Prisma.UserWhereInput` used by both `findMany` and `count`; `src/components/admin/UsersFilters.tsx` (client, debounced search box + segmented role/status buttons) pushes the params and drops `page` so a changed filter returns to page 1. Same shape works for the other admin lists when they need it.
- The **audit log** (`/dashboard/admin/audit`) has the same treatment (2026-09-09): `?q=` (matches `actorEmail` / `action` / `targetId`, `contains` insensitive), `?cat=` (a category key → one or more `action` `startsWith` prefixes; `AUDIT_CATEGORIES` in the page, labels in `AuditFilters.tsx`), `?from=` / `?to=` (`YYYY-MM-DD`, clamped to start/end of day, `createdAt` range). Clauses are combined under `AND: Prisma.AuditLogWhereInput[]` (not a flat `OR`, since `q` and `cat` each contribute their own `OR`). `src/components/admin/AuditFilters.tsx` is the client control (debounced search + native `<select>` + two `<input type=date>`). `ACTION_LABELS` on the page now covers every action string emitted by `logAudit` — keep it in sync when adding a new audited action.
- `next.config.ts` allows any HTTPS host for `next/image` (`remotePatterns: [{ protocol: "https", hostname: "**" }]`) because course thumbnails are arbitrary admin-supplied URLs, not from a fixed CDN — this is safe because only `requireAdmin()`-gated routes can set `thumbnailUrl`, not end users.
- **Rate limiting (`src/lib/rate-limit.ts`) now has two backends** (2026-09-06): **Upstash Redis** (`@upstash/redis`, fixed-window `INCR`+`PEXPIRE`) when `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are set — a real shared store that works correctly across multiple instances and serverless deployments — or an **in-memory fallback** otherwise (fine for local dev/a single long-running process, but does NOT work correctly on serverless platforms like Vercel, where each request can hit a different instance with its own empty memory). `checkRateLimit()` is now `async` — every call site must `await` it. Upstash's free tier is genuinely free (500K commands/month, no credit card) — code is ready and fallback-tested, but the Redis path itself hasn't been exercised end-to-end since no real Upstash credentials exist yet (same pattern as SendGrid). The in-memory fallback also got a periodic sweep (`SWEEP_INTERVAL_MS`) to fix a real unbounded-memory-growth bug — it previously never evicted expired buckets.
