# Ledger Academy — Project Rules

See `PROJECT_STATE.md` for full architecture/status. Rules below are things that have already caused real bugs or confusion in this project — read before making changes in these areas.

## Content & language
- **Never use the word "مدرس" anywhere in the UI.** Use "محاضر" or "مدرب" instead. This is a hard, non-negotiable rule for this platform.
- **All API error messages must be Arabic**, since `data.error` strings are shown directly to users in the UI. A 2026-09-06 audit found ~15 API route files still returning English guard-clause errors ("Forbidden", "Unauthorized", "Invalid input.") left over from early scaffolding while newer business-logic errors were correctly Arabic — all were translated. Don't reintroduce an English literal in a `NextResponse.json({ error: ... })` call.
- All user-facing UI is Arabic RTL (dark navy / gold theme, Cairo font). `lang="ar" dir="rtl"` and the Cairo font are now set **once, globally, on the root `<html>`/`<body>`** in `src/app/layout.tsx` — don't remove that. Per-page `dir="rtl" lang="ar"` wrapper divs still exist in most pages as a harmless leftover from before this was centralized; no need to strip them, but don't rely on them being the only source of RTL/font — the root layout is now the source of truth.
- **`/privacy` and `/terms` are real, tailored pages** (`src/app/(marketing)/privacy`, `.../terms`), not boilerplate — added 2026-09-06 because students are minors and the platform previously had zero data/legal disclosure anywhere. Both carry a visible disclaimer that they're a general template needing real lawyer review, not certified legal advice — don't remove that disclaimer, and don't present either page as legally final without the user confirming a lawyer reviewed it.

## Design system
- **shadcn/ui was added (2026-09-06)** — `components.json` (`style: radix-nova`, `rsc: true`, `rtl: true`), `src/lib/utils.ts` (`cn()`, re-exported from the `cn` npm package), components land in `src/components/ui/`. Add new primitives with `npx shadcn@latest add <name> -y`. **Its default init injects a generic light-mode-plus-`.dark`-class color system that does NOT match this app's theme** — this app is permanently dark (no light/dark toggle anywhere), so the semantic tokens (`--background`, `--foreground`, `--primary`, `--card`, `--border`, `--ring`, `--chart-1..5`, `--sidebar-*`, etc.) were manually remapped in `globals.css`'s single `:root` block directly onto the navy/gold palette instead (`--primary: #fbbf24`, `--background: #020617`, `--border: rgba(255,255,255,0.1)`, etc.) — the generated `.dark` class block was deleted since it would never apply. **If `npx shadcn add` is ever re-run and regenerates/duplicates this block, re-apply the navy/gold mapping — don't leave shadcn's default gray/white values in place**, or new components will render in the wrong (light, gray) theme. `--font-sans` is pointed at `var(--font-cairo)` (not a separate Geist font — init tried to add one; removed, this app is Arabic/Cairo-only per the rule below).
- **`framer-motion` and `recharts` were added (2026-09-06)** for animations and data-viz respectively — both plain npm packages, no account/config needed. Motion needs Client Components (`"use client"`); keep data-fetching in the Server Component page and pass plain serializable props down to a motion-enabled Client Component, rather than converting whole pages to client-side.
- Real design tokens live in `src/app/globals.css`'s `@theme` block: `--color-navy-*`/`--color-gold-*`, `--radius-card`/`--radius-control`, `--shadow-card`/`--shadow-elevated`/`--shadow-glow-gold`, `--animate-fade-in`/`-scale-in`/`-slide-up`/`-pop`. Before, `globals.css` was the untouched Next.js starter file with zero brand tokens — that's why the app had no shadows/elevation anywhere and inconsistent border-radius. **Use these tokens (`shadow-card`, `rounded-card`, `rounded-control`, `animate-*`) on new cards/surfaces instead of ad-hoc `rounded-2xl`/`shadow-none` guessing.**
- `slate-950`/`slate-900` and `navy-950`/`navy-900` are the same colors — the whole codebase was mass-renamed to `navy-*` (2026-09-06) for one consistent vocabulary. Don't reintroduce bare `slate-950`/`slate-900`/`amber-*` in new code.
- **Accessibility audit (2026-09-06, static code review only — no browser/device testing tool was available)**: images have proper `alt` text (only one real image exists in the app so far), all icon-only buttons have `aria-label`, and no keyboard-trap `onClick`-on-`<div>` patterns exist anywhere — everything interactive is a real `<button>`/`<a>`/`<Link>`. Found and fixed one real, calculated issue: `text-slate-500` on the `navy-950` background computes to a 4.24:1 contrast ratio, just under the WCAG AA minimum (4.5:1) for normal text — bumped to `text-slate-400` (7.87:1) everywhere it was real visible content (33 occurrences across 21 files), left `placeholder:text-slate-500` alone since placeholder contrast is a weaker WCAG requirement and a different UX convention. `gold-400` on `navy-950` computes to ~12:1 (excellent). Form inputs use `focus:outline-none` and rely solely on a `focus:border-gold-400` color change as their keyboard-focus indicator — legitimate but worth knowing if focus visibility is ever reported as an issue. **Real device/viewport/screen-reader testing has still never been done** — this was a code-level audit only.
- Duplicated JSX is a real recurring problem here (the course-card markup was copy-pasted verbatim across two pages before being extracted into `src/components/ledger-academy/CourseCard.tsx`) — if you're about to paste the same card/block into a second file, extract a shared component instead.
- `sonner` (toasts, mounted globally in `src/components/providers.tsx`) and `canvas-confetti` are installed for student-facing feedback (lesson complete, quiz pass). Reuse these rather than adding a different toast/confetti library.
- **Reading `localStorage` in a client component: use `useLocalStorage` from `src/lib/use-local-storage.ts`, not `useEffect(() => setState(localStorage.getItem(...)))`.** The `eslint-plugin-react-hooks` v6 rules that ship with Next 16 (`react-hooks/set-state-in-effect`) flag the effect pattern as an error, and it also causes an SSR/first-paint flash. The hook wraps `useSyncExternalStore` (server snapshot returns `null`, so no hydration mismatch), keeps multiple instances on the same key in sync within the tab via a custom event, and falls back to an in-memory store if `localStorage` itself throws (Safari "block all cookies", some webviews) so controlled inputs still work. `AnnouncementBanner`, `LessonWorkspacePanel`, and `SwotBoard` all use it.

## Routing
- **Dashboard routes are real folders (`src/app/dashboard/admin`, `src/app/dashboard/student`), never a `(dashboard)` route group.** A route group's parentheses are stripped from the URL — using one here would silently break the middleware matcher (`/dashboard/:path*`) and every existing link. This was deliberately fixed once already; don't reintroduce it.
- Login redirects by role: `ADMIN` → `/dashboard/admin`, everyone else → `/dashboard/student`. Don't hardcode a single redirect target.

## Security-critical invariants (found broken once, must never regress)
A full audit on 2026-09-06 found and fixed several real, exploitable bugs. These are now-enforced invariants — don't remove the checks that make them true:
- **Every route that writes `LessonProgress` or `QuizAttempt` (or renders lesson/quiz content) must verify the caller is enrolled in that content's course** (`db.enrollment.findUnique({ where: { userId_courseId: {...} } })`). Before the fix, `/api/progress`, `/api/quizzes/[id]/attempts`, and the lesson-detail page all trusted a client-supplied `lessonId`/`quizId` with no ownership check — meaning any logged-in user (even paying for nothing) could fabricate progress, harvest quiz answer keys (`correctId` was returned in the response), and read paid lesson content by guessing/observing IDs, none of which are secret (they're plain cuids visible in network requests). If you add a new student-facing route that reads/writes per-lesson or per-quiz data, it needs this same check.
- **Enrollment (`Enrollment` row creation) happens in exactly these places, nowhere else.** Do not add a "just create an Enrollment row" endpoint — a `POST /api/enrollments` used to exist that skipped every check, letting any user enroll in any paid course for free. It was deleted, not fixed.
  - `/api/checkout`: **free courses only** now (`price <= 0` → `enrollment.upsert`; paid → 403). Stripe was removed entirely (2026-09-07) — it never supported Egypt-based merchants. No online card payment anywhere in the app.
  - `/api/prepaid-codes/redeem`: a student submits a `PrepaidCode` (single-use, course-scoped, generated in batches by the admin at `/dashboard/admin/prepaid-codes`). Guarantees that must not regress: **(1)** the single-use claim is an atomic `updateMany({ where: { id, isUsed: false } })` inside a `$transaction` with the `enrollment.create` — a racing second redeem updates 0 rows and gets 409; **(2)** if `enrollment.create` throws `P2002` the whole transaction rolls back, so the code is **not** burned; **(3)** an explicit pre-check rejects redemption (without consuming the code) when the student is already enrolled; **(4)** an optional `courseId` in the body is verified against the code's own `courseId`; **(5)** rate-limited per user and per IP. Regression tests: `tests/api/prepaid-code-redeem.test.ts`.
  - `/api/code-orders` review (admin approve): approving a pending `CodeOrder` issues a `PrepaidCode` (already `isUsed`, `usedById` = the requester) **and** creates the `Enrollment`, in one `$transaction`. This is how a student "buys" access for a paid course — they submit a request with a manual-payment reference, the lecturer verifies the transfer offline and approves. (Added 2026-09-07 alongside the Stripe removal.)
- **Deleting a `Lesson` or `Module` must clean up `LessonProgress` and `Quiz`/`QuizAttempt` first**, inside a transaction, before the delete — both FKs are `ON DELETE RESTRICT` in the schema, so a naive `db.lesson.delete()`/`db.module.delete()` throws an uncaught 500 the moment any student has interacted with that lesson. `src/app/api/lessons/[id]/route.ts` and `src/app/api/modules/[id]/route.ts` show the correct pattern (mirrors the pre-existing, correct `QuizAttempt` cleanup in `src/app/api/quizzes/[id]/route.ts`).
- **`/api/auth/otp/send` deletes any previous unverified code for that email+purpose before creating a new one.** Without this, requesting a resend and then entering the *first* email's code fails against the newer DB row and burns an attempt on a code the user never typed — `otp/verify` only ever checks the single latest row by design, so there must only ever be one live row.

## Testing
- `npm test` (Vitest) runs regression tests for the 5 security-critical invariants above — this project had **zero automated tests** until 2026-09-06; before this, every fix was only verified once by hand and had no protection against silently regressing later.
- Tests run against a **dedicated Neon branch named `test`** (copy-on-write off production, created via `neon branches create --name test`), never the real dev/production database. Its connection string lives in `.env.test` (gitignored). `tests/setup.ts` loads it with `override: true` and hard-fails if `DATABASE_URL` doesn't contain that branch's host — this is a deliberate safety guard, don't remove it.
- `next-auth`'s `getServerSession` is mocked per test file (`vi.mock("next-auth", ...)`) to control the caller's identity/role; routes are imported and invoked directly (`POST(request)`, `DELETE(req, { params })`) rather than through a running server.
- **Always create/tear down fixtures via `tests/helpers/fixtures.ts`** (`createUser`, `createCourse`, `createLessonWithQuiz`, `enroll`, `cleanupCourse`, `cleanupUser`), never raw `db.course.delete()`/`db.user.delete()` in a test file directly. `Enrollment`, `LessonProgress`, and `Quiz`/`QuizAttempt` all have `RESTRICT` foreign keys back to `Course`/`User`/`Lesson` — deleting a course or user that still has an enrollment (or similar) silently fails if the call is wrapped in `.catch(() => {})`, which is exactly the leak this project's own tests hit once already (two test files bypassed the shared helper and it took a manual DB check to notice the test branch was accumulating leftover fixtures across runs). `cleanupCourse` handles the correct deletion order; use it.
- Coverage today is deliberately a starting slice, not exhaustive: the enrollment-IDOR fix (`/api/progress`), the quiz answer-key/paywall fix (`/api/quizzes/[id]/attempts`), both delete-cascade fixes (`/api/lessons/[id]`, `/api/modules/[id]`), the OTP-resend-invalidation fix, a static guard that `/api/enrollments` was never recreated, and prepaid-code redemption (`tests/api/prepaid-code-redeem.test.ts` — single-use, course-scope, no-double-grant). The lesson-order-collision fix doesn't have a test yet.

## Pricing & payments
- **There is no online payment integration.** Stripe was removed on 2026-09-07 (it never supported Egypt-based merchants, and Paymob/Fawry need a business registration the owner doesn't have yet). A course's `price` is a **display figure only** — it tells the student how much to transfer manually (Vodafone Cash / InstaPay / bank / cash). Access is then granted by a prepaid code or an approved `CodeOrder` (see the enrollment invariant above). Do not re-add a card-payment SDK/route without an explicit decision.
- Course prices are **Egyptian Pounds (ج.م)**, not USD. Use `formatEgp()` from `src/lib/format.ts` for display — never re-introduce `$`/`"usd"`.
- **Minimum paid price is `MIN_EGP_PRICE` (20 ج.م) from `src/lib/pricing.ts`, or exactly 0 for free.** Enforced in the admin course-create/price-save routes; keep it — it's just a sanity floor now (the original reason, Stripe's per-currency minimum, is gone).
- Quiz/exam scoring must always be computed server-side. Never send `correctId` (or any answer key) to the client before grading.

## Forms & user input
- **Never auto-derive a URL slug from an Arabic title.** A naive `slugify()` that strips non-`[a-z0-9]` characters removes 100% of Arabic text, so it silently produces a garbage slug like `-` (which the old regex `^[a-z0-9-]+$` accepted as "valid," creating a real course with a broken URL). The course-creation form (`CreateCourseForm.tsx`) requires the admin to type the slug in English directly — don't try to reintroduce auto-fill-from-title. The slug regex (`createCourseSchema`) requires at least one real alphanumeric segment, not just hyphens; keep it that way.

## Authentication (email OTP)
- Signup and password reset both require a verified 6-digit OTP sent to the user's **email** (not phone/SMS — SMS was tried first but every provider, including Twilio and Firebase Phone Auth, charges per message with no real free tier, and Egypt is excluded from most trial programs). Signup is a two-step client flow: collect name/email/password → send OTP → verify + create account in one submit.
- OTP codes are 6 digits, **hashed with bcrypt before storage** (`OtpCode.codeHash`) — never store or log the plaintext code outside of `sendOtpEmail`'s dev-mode fallback.
- `src/lib/email.ts` sends via **SendGrid** (`@sendgrid/mail`) when `SENDGRID_API_KEY`/`EMAIL_FROM` are set; otherwise it logs `[EMAIL DEV MODE] to <email>: ...` to the server console so the flow is testable without a SendGrid account (same nullable-client pattern `src/lib/rate-limit.ts` uses for Upstash). Switched from Resend (2026-09-06) because Resend's free sender (`onboarding@resend.dev`) only delivers to the account owner's own address — SendGrid's single-sender verification lets `EMAIL_FROM` be any address the owner verifies (no domain purchase needed) and actually delivers to arbitrary student emails.
- A verified `OtpCode` row is **deleted** the moment it's consumed by `/api/register` or `/api/auth/reset-password` — this is the replay-protection mechanism. Don't switch to a boolean "used" flag without also enforcing single-use some other way.
- Both `/api/register` and `/api/auth/reset-password` require the matching `OtpCode.verifiedAt` to be within a 15-minute window — this is intentionally generous (not a short-lived token) so the client doesn't need a separate expiry countdown.
- OTP send/verify are rate-limited both by email and by IP (`checkRateLimit`) — keep both when touching these routes.
- There is no phone number field anywhere in this app — it was added, then removed, during the OTP channel pivot. Don't reintroduce one without a real reason.
- **Admin lockout recovery**: `npm run admin:recover -- --email you@example.com --password "NewPass123"` (`scripts/admin-recovery.ts`) sets a user's password directly in the database and forces `role: ADMIN`, bypassing the email-OTP flow entirely — created 2026-09-06 because this project has only ever had a single ADMIN account, and normal password reset for that account depends on the same email system that isn't always working (a real, previously-unrecoverable lockout risk). Requires direct filesystem/`DATABASE_URL` access already, so it adds no new attack surface. Upserts by email, so it also works to bootstrap a fresh admin from scratch if the database ever loses its only one.

## Admin control over student-facing content
- Site-wide content the admin should control (not hardcode) lives in the `SiteSettings` singleton model (`id: "main"`, fetched/created via `getSiteSettings()` in `src/lib/site-settings.ts`) — currently: homepage student-count/satisfaction-rate stats, contact email/phone, per-tool visibility toggles (`showBreakEvenTool`, `showSwotTool`), the student-dashboard `announcement`/`announcementActive` banner, and `paymentInstructions` (shown in the "اطلب كودًا للكورس" form on paid course pages). All edited at `/dashboard/admin/settings` via `SiteSettingsForm` → the audit-logged `PATCH /api/settings`. If the admin needs control over more site content, extend this model rather than inventing a second settings mechanism.
- `Course.thumbnailUrl` and full course details (title/description/grade) are now editable after creation via `/dashboard/admin/courses/[id]/edit` (`EditCourseDetailsForm.tsx` → `updateCourseSchema`) — don't reintroduce the old price/publish-only limitation.
- Modules (units) have real CRUD now (`POST /api/modules`, `DELETE /api/modules/[id]`) — previously they could only be created via `prisma/seed.ts`. There's still no reorder UI; `order` is set by append-length on create.
- Every destructive admin action (delete lesson/module/resource/question) must have a `confirm()` dialog — this was inconsistent before (only lesson delete had one) and has since been made consistent; keep it that way for any new delete button.

## Lesson videos
- Videos are hosted on **YouTube (uploaded as "Unlisted")**, not uploaded to app storage. This was a deliberate choice: Neon Object Storage was evaluated (already-connected, S3-compatible) but its free plan's 5GB/month bandwidth is shared across the whole app and would be exhausted fast by real video-streaming traffic — YouTube absorbs that cost forever regardless of scale. Don't build a file-upload-to-storage feature for lesson videos without re-raising this tradeoff with the user first.
- Admins paste a normal YouTube URL (`youtube.com/watch?v=...`, `youtu.be/...`, or `/shorts/...`) into the lesson's video-URL field — `src/lib/video-url.ts`'s `toEmbeddableUrl()` converts it to the `/embed/` form at render time in `VideoPlayer.tsx`, since YouTube refuses to load its normal watch links inside an `<iframe>`. The stored `Lesson.videoUrl` stays as whatever the admin actually pasted (not rewritten) — conversion is display-only.
- Direct video file URLs (`.mp4`/`.webm`/`.ogg`) still render as a native `<video>` tag instead of an iframe — that path is unaffected by the YouTube conversion.

## Database
- Database is **Postgres on Neon** (`prisma/schema.prisma` datasource is `postgresql`). Connection vars (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `NEON_BRANCH`) live in `.env` (pulled by the Neon CLI); app secrets (`NEXTAUTH_*`, `SENDGRID_*`, `UPSTASH_*`) live in `.env.local`. Next.js loads `.env` then `.env.local` with `.env.local` taking precedence — **don't put `DATABASE_URL` in `.env.local`**, it would silently shadow the real one.
- This project has no migration history — schema changes are applied with `npx prisma db push`, not `migrate dev`. A warning about a new unique/required column is usually a false positive on a table with no conflicting data; read it before blindly re-running with `--accept-data-loss`.
- Don't upgrade `prisma`/`@prisma/client` past the v6 line without checking first — v8 ("Prisma Developer Platform") has a completely different CLI with no `migrate dev`/`generate` commands and broke the whole workflow when it got installed once by default.
- After schema changes, **restart the dev server** — a long-running `next dev` process holds a stale `@prisma/client` in memory even after `prisma db push` regenerates it on disk, and will 500 on any new field/model until restarted. On Windows this can also show as `EPERM` renaming the query engine `.dll`; kill stray node processes on port 3000 and retry.
- The old local `prisma/dev.db` SQLite file and the stale SQLite-dialect `prisma/migrations/` folder were both deleted (2026-09-06) — inspected first via Node's built-in `node:sqlite`, confirmed everything in it (2 placeholder test users, a junk "koko" lesson, an empty quiz, zero enrollments) was throwaway test data with no real content, and the courses/lessons were already duplicated in Postgres from the seed. Nothing to migrate.
- **The Neon project is on the free plan, with only 6 hours of point-in-time-recovery history** (`history_retention_seconds: 21600`, checked via `neon projects list -o json`, 2026-09-06). If data is destroyed and not noticed within 6 hours, it's gone. Upgrading for longer retention is a cost decision — don't assume more backup protection exists than this without re-checking.

## Performance (pre-scale prep)
- Public marketing pages with no per-user server-rendered content (`(marketing)/page.tsx`, `(marketing)/courses/page.tsx`, `(marketing)/pricing/page.tsx`) use `export const revalidate = 300` (ISR) instead of `force-dynamic`, to cut database load on the highest-traffic pages. **`(marketing)/courses/[slug]/page.tsx` deliberately stays `force-dynamic`** — it reads `getServerSession` server-side to render a personalized enroll-button state, and caching that would risk showing one user's enrollment status to another. Don't convert it to ISR without removing that per-request session read first.
- Admin list pages (`users`, `progress`, `courses`) are paginated (`PAGE_SIZE = 20`, `skip`/`take` in Prisma, shared `src/components/admin/Pagination.tsx` component reading a `?page=` search param). Follow this exact pattern for any new admin list rather than an unbounded `findMany`.
- `next.config.ts` allows any HTTPS host for `next/image` (`remotePatterns: [{ protocol: "https", hostname: "**" }]`) because course thumbnails are arbitrary admin-supplied URLs, not from a fixed CDN — this is safe because only `requireAdmin()`-gated routes can set `thumbnailUrl`, not end users.
- **Rate limiting (`src/lib/rate-limit.ts`) now has two backends** (2026-09-06): **Upstash Redis** (`@upstash/redis`, fixed-window `INCR`+`PEXPIRE`) when `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` are set — a real shared store that works correctly across multiple instances and serverless deployments — or an **in-memory fallback** otherwise (fine for local dev/a single long-running process, but does NOT work correctly on serverless platforms like Vercel, where each request can hit a different instance with its own empty memory). `checkRateLimit()` is now `async` — every call site must `await` it. Upstash's free tier is genuinely free (500K commands/month, no credit card) — code is ready and fallback-tested, but the Redis path itself hasn't been exercised end-to-end since no real Upstash credentials exist yet (same pattern as SendGrid). The in-memory fallback also got a periodic sweep (`SWEEP_INTERVAL_MS`) to fix a real unbounded-memory-growth bug — it previously never evicted expired buckets.

## Dev workflow
- **Git**: this project had no git repository at all until 2026-09-06 — every prior change (including deletions) had zero rollback safety net. It's now initialized (`main` branch), with commit identity scoped locally to this repo only (`user.name "omar"`, `user.email "omarhamuda200@gmail.com"`) rather than set globally. `.gitignore` excludes `.env*` except `.env.example` (a real template with placeholder values, safe to commit). Commit real, reviewable chunks of work going forward instead of letting changes pile up uncommitted.
- Before starting `npm run dev`, check for and kill any stray leftover dev server (`netstat -ano | grep 3000`) — a stale process from a previous session can serve confusing "current" behavior against outdated code and has caused real debugging confusion here.
- When verifying a fix or feature, actually drive it in a browser (Playwright) end-to-end rather than trusting a build pass alone — several real bugs in this project (server/client boundary crash passing lucide icons, Stripe locale error, price-too-low error) were only caught this way, not by `npm run build` or types.
- **Testing an API with Arabic text via `curl -d` on Git Bash/Windows silently corrupts it to `?????`** — this is a shell command-line encoding issue, not a bug in the app. Write the JSON body to a file (UTF-8) and use `curl --data-binary @file.json` instead when a test payload contains Arabic text.
